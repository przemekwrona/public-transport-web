# DigitalOcean: VPN i Keycloak

Oba serwery to droplet z Marketplace. Stoją w VPC `10.114.16.0/24`.

| Rola | Źródło | Adres w VPC | Adres publiczny |
| --- | --- | --- | --- |
| OpenVPN | Marketplace OpenVPN | `10.114.16.3` | endpoint VPN |
| Keycloak | Marketplace Keycloak | `10.114.16.5` | `165.227.164.66` |
| Postgres | Managed Database | host prywatny, port `25060` | nieużywany |

Prywatny host bazy: `private-nastepna-stacja-fran-db-do-user-4741697-0.j.db.ondigitalocean.com`.

Baza Keycloak: `public_transport_keycloak_db`. Użytkownik i właściciel: `public_transport_keycloak`.

## OpenVPN

Droplet VPN jest w tym samym VPC co Keycloak. Połączenie z laptopa kończy się na tym droplecie, dlatego SSH na sam serwer VPN działa bez dodatkowej trasy.

Ruch do innych dropletów w VPC musi wyjść z karty prywatnej z adresem `10.114.16.3`. DigitalOcean odrzuca pakiety, których źródłem jest sieć klientów OpenVPN (zwykle `10.8.0.0/24`). Na serwerze VPN włączone jest przekazywanie i maskarada, więc Keycloak widzi połączenie jako przychodzące z dropletu VPN.

Na droplecie OpenVPN:

```bash
sysctl -w net.ipv4.ip_forward=1
echo 'net.ipv4.ip_forward=1' > /etc/sysctl.d/99-ip-forward.conf

# eth1 to karta z adresem 10.114.16.3; nazwę potwierdza: ip -4 addr
iptables -t nat -A POSTROUTING -s 10.8.0.0/24 -o eth1 -j MASQUERADE
iptables -A FORWARD -i tun0 -o eth1 -j ACCEPT
iptables -A FORWARD -i eth1 -o tun0 -m state --state RELATED,ESTABLISHED -j ACCEPT
```

W konfiguracji serwera OpenVPN klienci dostają trasę do VPC:

```
push "route 10.114.16.0 255.255.255.0"
```

Przy UFW: `DEFAULT_FORWARD_POLICY="ACCEPT"` w `/etc/default/ufw`, a reguła `MASQUERADE` w `/etc/ufw/before.rules` (sekcja `*nat`, przed `*filter`). Bez UFW reguły zapisuje `netfilter-persistent`.

Po zmianie trasy klient VPN rozłącza się i łączy ponownie.

Cloud Firewall na innych dropletach może mieć jako źródło droplet VPN. Po maskaradzie źródłem pakietu jest `10.114.16.3`. Wpis `10.114.16.3/32` ogranicza regułę do adresu prywatnego. Wybranie dropletu z listy puszcza też jego adres publiczny.

Sam SSH między dropletami, bez ruchu z laptopa, idzie po adresie prywatnym:

```bash
ssh -i ~/.ssh/id_ed25519_digitalocean root@10.114.16.5
```

## Keycloak

Obraz Marketplace trzyma Keycloak w kontenerze Dockera `keycloak` (obraz budowany lokalnie jako `local-keycloak`, katalog `/var/digitalocean`). Kontener działa z `--network=host`. Nginx na hoście słucha na porcie 80 i przekazuje ruch do `https://localhost:8443`. Port 9000 to interfejs metryk, Nginx wystawia go na 9001. Hasła admina, bazy z pierwszego startu i keystore są w `/root/.digitalocean_passwords`.

Postgres 16 z obrazu Marketplace jest usługą systemu (`postgresql.service`), nie kontenerem. Keycloak został od niego odpięty i korzysta z zarządzanej bazy w VPC. Po przełączeniu lokalną usługę można wyłączyć:

```bash
systemctl disable --now postgresql
```

W bazie zarządzanej schemat `public` należy do `public_transport_keycloak`. W Postgresie 15+ samo `GRANT` na bazę nie daje prawa tworzenia tabel. Jako `doadmin`, będąc połączonym z `public_transport_keycloak_db`:

```sql
ALTER DATABASE public_transport_keycloak_db OWNER TO public_transport_keycloak;
ALTER SCHEMA public OWNER TO public_transport_keycloak;
GRANT ALL ON SCHEMA public TO public_transport_keycloak;
```

Kontener (hasło bazy nie jest zapisane w tym pliku):

```bash
set -a
. /root/.digitalocean_passwords
set +a

export KC_DB_PASSWORD='HASLO_UZYTKOWNIKA_public_transport_keycloak'

docker rm -f keycloak

docker run -d --network=host \
  --name keycloak \
  --restart unless-stopped \
  -e KEYCLOAK_ADMIN=admin \
  -e KEYCLOAK_ADMIN_PASSWORD="${KEYCLOAK_ADMIN_PASSWORD}" \
  -e KC_DB=postgres \
  -e KC_DB_URL='jdbc:postgresql://private-nastepna-stacja-fran-db-do-user-4741697-0.j.db.ondigitalocean.com:25060/public_transport_keycloak_db?sslmode=require' \
  -e KC_DB_USERNAME=public_transport_keycloak \
  -e KC_DB_PASSWORD="${KC_DB_PASSWORD}" \
  -e KC_HOSTNAME='http://10.114.16.5' \
  -e KC_HOSTNAME_ADMIN='https://10.114.16.5:8443' \
  local-keycloak \
  start \
  --https-key-store-password="${KEYSTORE_PASSWORD}" \
  --optimized
```

`KC_HOSTNAME` to adres logowania. `KC_HOSTNAME_ADMIN` to panel admina. Oba są na droplecie Keycloak. Droplet VPN jest tylko drogą i źródłem w firewallu.

`sslmode=require` jest wymagany przez zarządzany Postgres. Droplet Keycloak jest na liście trusted sources tej bazy.

### Firewall dropletu Keycloak

Reguły są w Cloud Firewall DigitalOcean przypisanym do dropletu Keycloak. Źródłem jest droplet VPN, nie cały internet.

| Port | Rola | Źródło |
| --- | --- | --- |
| 22 | SSH | droplet VPN |
| 80 | logowanie przez Nginx | droplet VPN |
| 443 | HTTPS | droplet VPN |
| 8443 | Keycloak, panel admina | droplet VPN |
| 9000 | metryki | droplet VPN |

Ruch wychodzący zostaje otwarty, żeby kontener doszedł do bazy na porcie `25060`.

Plik `/etc/nginx/sites-available/keycloak` nie zamyka dostępu z internetu. Robi to firewall. Nginx warto zmienić tylko wtedy, gdy sam adres `http://10.114.16.5` ma otwierać ekran logowania zamiast przekierowania na panel admina. Wtedy nad `location /` dochodzi:

```nginx
location = / {
    return 302 /realms/master/account;
}
```

### Wejście po VPN

Po połączeniu z OpenVPN:

- logowanie: `http://10.114.16.5` albo `http://10.114.16.5/realms/master/account`
- panel admina: `https://10.114.16.5:8443` (certyfikat z obrazu Marketplace jest samopodpisany)
- użytkownik panelu: `admin`, hasło `KEYCLOAK_ADMIN_PASSWORD` z `/root/.digitalocean_passwords`

Realm `public-transport` z repozytorium nie jest wgrany na ten serwer. Obraz Marketplace nie importuje `keycloak/import/public-transport-realm.json`.
